# Сеть безопасности под рефакторинг

Одна команда на весь цикл:

```powershell
.\tools\Verify.ps1              # сборка + юнит-тесты + регрессия проб (~50 с)
.\tools\Verify.ps1 -SkipProbes  # только сборка и тесты (~10 с), для проверки на ходу
```

Зелёный `Verify.ps1` означает: перенос кода между проектами и распил файлов не изменили
поведение. Красный означает, что шаг был не механическим, — и показывает, где именно.

## Из чего она состоит

### 1. Юнит-тесты (`DecaEngine.Tests`)

Чистая логика: массивы на входе, массивы на выходе, ни графического API, ни файлов. Покрыто то,
что предстоит выносить из больших файлов, — чтобы переезд было чем проверить.

```powershell
dotnet test DecaEngine.Tests\DecaEngine.Tests.csproj -c Debug -p:Platform=x64
```

### 2. Регрессия проб (`Run-ProbeSuite.ps1`)

Тестов на рендер нет и быть не может: проверять картинку ассертами дороже, чем её рисовать. Зато
гарнессы `DECA_PROBE_*` уже печатают числа, по которым видно, **что именно** сломалось, — светимость
кадра по каналам, границы сцены, поле probe GI, отчёт по клипам, состояние стриминга. Скрипт
превращает эти числа в эталон и сверяет с ним.

```powershell
.\tools\Run-ProbeSuite.ps1                            # сверить с эталоном
.\tools\Run-ProbeSuite.ps1 -Scenario physics          # один сценарий
.\tools\Run-ProbeSuite.ps1 -Baseline                  # ПЕРЕЗАПИСАТЬ эталон
.\tools\Run-ProbeSuite.ps1 -Backend vulkan            # другой бэкенд
```

Восемь сценариев, 238 метрик: превью Sponza, интерьер с точечным светом, GPU-путь probe GI,
импорт анимации и разметка аватара на Fox, мир Bepu, геймплейные системы, полный цикл обоих
рендер-графов.

**`-Baseline` — только на заведомо исправном дереве.** Обычно сразу после коммита, который прошёл
сверку. Перезаписать эталон на сломанном дереве значит узаконить поломку — после этого набор врёт,
а набор, который врёт, перестают запускать.

Эталоны лежат в `tools/probe-baseline/*.metrics` и версионируются: расхождение видно в диффе.

## Что в эталон не попадает и почему

| Выбрасывается | Причина |
|---|---|
| строки с ` ms` | времена зависят от загрузки машины |
| абсолютные пути | привязали бы эталон к конкретной машине |
| счётчики compile / pso | зависят от состояния `DECA_SHADER_CACHE` |
| `[diligent-*]` | лог драйвера: адреса страниц памяти не совпадают между двумя запусками |
| `[...] frame N:` | вехи асинхронного стриминга гуляют на кадр-другой от фоновых потоков |

Числа сверяются с относительным допуском (по умолчанию 1%), текст — точно. У `full-loop` свой
допуск 10%: его итоговая строка несёт номера кадров дозагрузки, но главное в ней — текст
`HasModel=True` и пустой `LoadError`, а он сверяется точно.

## Проверено, что сеть ловит

Обе половины проверены мутацией — зелёный набор ничего не доказывает, пока не увидишь, как он
краснеет:

- перевёрнутый знак битангента и поднятый потолок фиксированных лучей → юнит-тесты краснеют;
- отдача отскока probe GI 0.5 → 0.7 → расходятся `probe-gi field` и `debug_probes`.

## Ловушки

- **Платформа.** Diligent не работает на AnyCPU: везде `-p:Platform=x64`. Собранное с этим флагом
  ложится в `bin\x64\Debug\net10.0`, а в `bin\Debug\net10.0` остаётся СТАРЫЙ комплект, где exe
  обновляется, а `DecaEngine.Graphics.Diligent.dll` — нет. Запуск оттуда тихо гоняет вчерашний код.
- **BOM в `.ps1`.** Windows PowerShell 5.1 читает скрипт без BOM как ANSI, и русский текст
  превращается в мусор ещё на разборе. У скриптов здесь BOM есть — при правке не потерять.
